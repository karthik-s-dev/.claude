ev: E1
cls: MANDATED (ADR defaults) + VERIFIED implementation; deviation C-08
std: CTX-01, CTX-02, API-04, OBS-01
rel: request-context-propagation, structured-logging, request-header-management, distributed-request-tracking, trace-context-propagation, api-error-response
d: Use when adding or reviewing request tracing - accepting or generating the x-correlation-id at the edge, binding it to async context, echoing it in responses/errors/logs, and propagating it over HTTP and messages. Applies the organization's ADR defaults and flags the reference implementations' known gaps.
scope: Generation, validation, propagation and use of the correlation ID.
app: HTTP services and message flows; Node implementation with AsyncLocalStorage.
purpose: One ID follows a business request across services, logs, errors and async work.
when:
- Creating middleware or a new service.
- Making outbound HTTP calls or publishing messages.
- Debugging missing/unlinked logs.
org:
- MUST: Header is `x-correlation-id` (case-insensitive). Resolve-or-generate (`randomUUID()`) **before** auth and error handling; bind to `AsyncLocalStorage`; echo it as a response header, in every envelope `metadata.correlationId`, in every log line, on every outbound call and in message `applicationProperties.correlationId`. Never fatal when missing (`"unknown"`).
- MUST (ADR default): Public/untrusted callers' values are ignored and regenerated; a supplied value is kept only from a trusted internal caller; accepted IDs are validated (strict charset, max length); invalid ones are regenerated (no 400); **no** `x-request-id` fallback; the body/query can never set it; correlation, request ID and trace ID are three different identifiers.
- UNRESOLVED (C-08): Both reference implementations accept any non-empty inbound value and fall back to `x-request-id`, validate nothing, and have no trusted-caller mechanism. For new or modified code implement the ADR default if a trust mechanism is available; otherwise keep existing behaviour, add the validation (charset/length), and report the gap. Never widen acceptance.
- MUST: Exactly one correlation mechanism per service; do not run a parallel request-id system (reference defect `requestTelemetry.middleware`).
- MUST: Implement correlation helpers (`getOrCreateCorrelationId`, `runWithCorrelationId`, `getCorrelationId`) once in the service's shared-infra zone and reuse them everywhere (no duplicate copies, C-08).
impl:
- Mount the correlation middleware at the top of each router (before auth).
- Read `getCorrelationId()` in the logger wrapper, error middleware, outbound client builders and message producers.
- Validate inbound IDs against `^[A-Za-z0-9._:-]{8,128}$` (or the repo's rule) and regenerate otherwise.
- Wrap handlers mounted outside routers with `withCorrelationId`.
ex: ts | Middleware with validation (extends the reference with the ADR validation rule)
const ID_RE = /^[A-Za-z0-9._:-]{8,128}$/;
export function correlationIdMiddleware(req: Request, res: Response, next: NextFunction) {
  const raw = req.headers["x-correlation-id"];
  const supplied = (Array.isArray(raw) ? raw[0] : raw)?.trim();
  const id = supplied && ID_RE.test(supplied) && isTrustedCaller(req) ? supplied : randomUUID();
  req.correlationId = id;
  res.setHeader("x-correlation-id", id);
  runWithCorrelationId(id, () => next());
}
/ex

- Missing/invalid ID never fails the request; missing context yields `"unknown"` in envelopes and logs.
sec:
- Treat the header as untrusted input (log injection, cardinality); never reflect unvalidated values.
test:
- Untrusted valid ID regenerated; trusted valid kept; trusted invalid regenerated; body field ignored; ID present on 401/500 responses; present on outbound call.
anti:
- Trusting any caller's ID.
- `x-request-id` fallback.
- Passing the ID manually through every function signature.
- Reading from body.
check:
- Middleware before auth; ALS bound; header/envelope/log/outbound/message propagation; validation; tests.

@@ idempotency-management | Idempotency Management
ev: E2
cls: MANDATED (ADR defaults) / implementation UNRESOLVED (C-07)
std: CTX-03, CTX-04, API-10, RES-02
rel: request-deduplication, message-idempotency, usage-event-identity, api-request-structure, api-error-response, distributed-locking
d: Use when building or reviewing retryable write operations - Idempotency-Key header, scope, canonical request fingerprint, atomic claim, in-progress handling, replay, conflict, release on failure, retention and fail-open/closed policy. Applies the organization's ADR defaults and documents the reference Redis implementation's deviations.
scope: Idempotent API write operations and their stores.
app: HTTP write APIs; Redis (reference) or relational store (ADR default).
purpose: Safe client retries without double effects.
when:
- Adding a write endpoint that clients may retry.
- Reviewing idempotency handling in payments/usage/order-like flows.
org:
- MUST (ADR default): `Idempotency-Key` HTTP header is the only key source (no body fallback); mandatory on externally exposed writes - missing/invalid key -> 400; validated format and length.
- MUST: Key scope = authenticated tenant + operation + key. Fingerprint = SHA-256 of canonical JSON (sorted keys).
- MUST: Atomic claim (insert-if-absent / `SET NX`); on duplicate: completed -> replay the stored response; same key + different fingerprint -> **409 `IDEMPOTENCY_KEY_REUSED`**; still running -> wait at most 1 s then **409 `IDEMPOTENCY_IN_PROGRESS`** with `Retry-After`.
- MUST: Transient failures **release** the claim; the result is stored only after the operation is verified; a timed-out write releases the key and returns 504.
- MUST: Effect-level dedupe (deterministic event IDs, `usage-event-identity`) in addition, even when the store is healthy.
- MUST: Store outage on writes fails **closed** (503 + `Retry-After`); fail open only per operation with written approval naming the downstream dedupe.
- MUST: Retention 72 h standard; 7 days or more for financial/high-value; always longer than the client retry window.
- UNRESOLVED (C-07): Reference implementation uses a Redis store (`SET key EX ttl NX`, Lua compare-and-swap takeover), also reads a body key, and names conflicts `IDEMPOTENCY_KEY_CONFLICT` / `IDEMPOTENCY_REQUEST_IN_PROGRESS`; fail-open answers are replayed for 30 s / max 3 replays. ADR default prefers a relational store with a unique constraint. Follow the target repo's existing store; for **new** services use the ADR default or request approval for Redis; always use the ADR error codes in new code or add aliases.
impl:
- Resolve key from the header; validate; compute fingerprint over the validated body.
- Acquire: `new` -> process; `duplicate` -> replay stored summary; `in_progress` -> bounded wait/409; `conflict` -> 409.
- On success store `{bodyHash, resultSummary, recordedAt}`; on failure release.
- Add TTL/retention config per operation and a cleanup/expiry mechanism.
ex: ts | Claim with fingerprint (reference pattern, Redis)
const ok = await redis.set(key, JSON.stringify(record), "EX", ttlSeconds, "NX");
if (ok === "OK") return { status: "new" };
const existing = JSON.parse((await redis.get(key)) ?? "null");
if (existing && existing.bodyHash !== bodyHash) return { status: "conflict" };      // -> 409 IDEMPOTENCY_KEY_REUSED
return existing?.resultSummary === undefined ? { status: "in_progress" } : { status: "duplicate", resultSummary: existing.resultSummary };
/ex
fail:
- Store errors are surfaced (503), logged and alerted; never swallowed.
- Fail-open answers are marked and replayed only briefly and a bounded number of times.
sec:
- Key scoped by tenant so keys cannot collide across tenants; fingerprint excludes secrets from logs.
test:
- New, duplicate (replay), conflict, in-progress, timeout releases key, store outage 503, tenant isolation, concurrent duplicates.
anti:
- Key from body.
- Storing success before verification.
- Cache-only store with eviction and no effect-level dedupe.
- Global (unscoped) keys.
check:
- Header-only key; scope; fingerprint; atomic claim; 409 codes; release on failure; retention; effect-level dedupe; outage policy.
