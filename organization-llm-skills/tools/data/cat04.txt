@@ error-catalog-management | Error Catalog Management
ev: E1
cls: MANDATED (task + ARCH-LLD-003 / ADR-004) + VERIFIED
std: ERR-01, ERR-02, ERR-03, ERR-04, ERR-05, ERR-09, PKG-01
rel: error-code-standards, exception-to-error-mapping, global-exception-handling, api-error-response, business-exception-handling, technical-exception-handling
d: Use when adding, changing, deprecating or referencing an error in a service - the single typed error catalog, numeric/semantic codes, HTTP mapping, throw helpers and catch-all. This is the canonical error-catalog skill; always reuse it from API, integration, messaging and security work and never create a second error mechanism.
scope: Definition and use of the service error catalog.
app: Services using `@inextlabs/platform-errors` (Node/TypeScript reference).
purpose: Every failure has a stable identity (code + numericCode + HTTP status + safe message) defined in one place and thrown through one helper.
when:
- Any new failure path in application code.
- Adding or changing an error code.
- Reviewing code that throws `new Error(...)`, returns ad-hoc bodies or matches on message text.
org:
- MUST: One catalog per service as a `const` map; entries `{ numericCode | num, httpStatus | http, code, message }`; the service also defines `UNHANDLED_ERROR` (catch-all) - ERR-02.
- MUST: Errors are thrown as `AppError(statusCode, code, numericCode, message, details?)` from `@inextlabs/platform-errors`, via a catalog helper (`throwXError(key, details?)` or `appErr(entry, details?)`); never `throw new Error()` for expected failures.
- MUST: `numericCode` follows `PLATFORM_CODE + SERVICE_CODE + MODULE_NUM + SEQ` (8 digits; see `error-code-standards`); build it with the service's single local `makeErrorCode(ss, mm, seq)` helper (see `error-code-standards`).
- MUST: Codes are append-only: never reuse, renumber or rename; deprecate by comment, keep the entry.
- MUST: Messages are generic, safe, human-readable and **never** parsed by clients or code.
- MUST: Group entries and comment the scheme/ranges at the top; document reserved ranges in comments.
- VERIFIED: Reference service A groups by HTTP category with reserved ranges; reference service B groups by `MM` source-file with a header table (C-01). Follow the target's grouping.
- MUST: Add a catalog test (see Testing) that fails on duplicate numeric codes, malformed codes, and status/category mismatches (GENERIC addition; present partially in `error-catalog.test.ts` of the enforcement repo).
impl:
- Open the target's catalog; find the banding/MM rules in its header comment.
- Pick the next free sequence in the right band/module; add the entry; write the test assertion.
- Throw with safe `details` only.
- Update OpenAPI error responses and docs.
ex: ts | Catalog entry and helper (reference shape)
export const ErrorCatalog = {
  // 1xxx: Validation (400)
  VALIDATION_FAILED: { numericCode: makeErrorCode(SS, MM, 3), httpStatus: 400, message: "Request validation failed" },
  CLIENT_CONFIG_NOT_FOUND: { numericCode: makeErrorCode(SS, MM, 13), httpStatus: 404, message: "Client configuration not found" },
  UNHANDLED_ERROR: { numericCode: makeErrorCode(SS, MM, 51), httpStatus: 500, message: "An unhandled error occurred" },
} as const;
export type ErrorCodeKey = keyof typeof ErrorCatalog;
export function throwServiceError(key: ErrorCodeKey, details?: unknown): never {
  const e = ErrorCatalog[key];
  throw new AppError(e.httpStatus, key, e.numericCode, e.message, details);
}
/ex
fail:
- Unknown thrown values are wrapped as `UNHANDLED_ERROR` at the boundary (`exception-to-error-mapping`).
sec:
- Messages must not reveal existence of resources to unauthorized callers where that matters; no stack/driver text.
test:
- Catalog test: all `numericCode` unique, match `/^1\d{7}$/`, status within allowed set; each key referenced in code exists.
anti:
- Second catalog or enum for the same service.
- `code` derived from message text.
- Renumbering existing entries.
- Using error codes of another service.
check:
- Entry appended; unique; helper used; test updated; docs updated.

@@ error-code-standards | Error Code Standards
ev: E1
cls: MANDATED (task + ADR-004); MM policy UNRESOLVED (C-01)
std: ERR-03, ERR-04
rel: error-catalog-management, exception-to-error-mapping, api-error-response, breaking-change-review, api-compatibility-review
d: Use when constructing, validating or reviewing numeric error codes - PLATFORM_CODE + SERVICE_CODE + MODULE_NUM + sequence (001...) - choosing module numbers and sequences, registering a service number, or detecting duplicates and legacy code schemes.
scope: Error-code composition, registry and uniqueness rules.
app: All services; a small local `makeErrorCode` helper in each service's error module.
purpose: Greppable, stable, service-encoded codes that never collide across the platform.
when:
- Creating the first catalog of a new service.
- Adding a module/area to a catalog.
- Reviewing code that builds codes by hand or uses `50xxx` / `INXT50xxx`.
org:
- MUST: `numericCode = PLATFORM_CODE + SERVICE_CODE + MODULE_NUM + SEQ` as an **8-character string**: `PLATFORM_CODE` = `1` (always, 1 digit); `SERVICE_CODE` = 2 digits, zero-padded, registered per service in the organization's service-code registry (observed: config 02, enforcement 03, ingestion 04, rollup 05, portal 06 - registry owner/location to be confirmed); `MODULE_NUM` = 2 digits, zero-padded; `SEQ` = 3 digits starting `001`, zero-padded. Example `makeErrorCode(3, 0, 1) -> "10300001"`.
- MUST: Human-readable service prefix (when needed in a code string) is `"INXT1" + SS` (for example `INXT103`).
- MUST: New services register a **new** `SERVICE_CODE` in the service-code registry; never reuse another service's.
- MUST: Uniqueness is per `(SERVICE_CODE, MODULE_NUM, SEQ)`; a number is never reused or changed once released; duplicates are prevented by a catalog test and code review.
- MUST: `SERVICE_CODE` is a single constant imported by the catalog and the logger configuration (reference defect: `"02"` in the catalog vs `"102"` in logger bootstrap); do not read it from env with literal fallbacks.
- VERIFIED: Sequence banding (service-registry convention + config catalog): 001-010 validation(400) · 011 authentication(401) · 012 authorization(403) · 013-022 not found(404) · 023-034 infrastructure(500) · 035-048 business logic · 049-050 external dependency(502/503) · 051-052 catch-all(500).
- UNRESOLVED (C-01): `MODULE_NUM` policy - reference service A fixes `00` and uses banding; reference service B uses `MM` = source file/area (01..07) with per-file sequences and no banding. Follow the target repo's policy; do not change codes already shipped; propose (do not decide) a functional-module policy.
- MUST NOT extend legacy schemes: `error-codes.ts` (`50` + HTTP status, e.g. `50404`) and vendored `HttpError` (`INXT50` + HTTP status) - they are legacy (C-01).
impl:
- Read the target catalog header for its MM/banding rules and the service registry for `SERVICE_CODE`.
- Compute the code with the local helper `makeErrorCode(ss, mm, seq)` = `"1" + pad2(ss) + pad2(mm) + pad3(seq)`; never concatenate by hand elsewhere.
- Add a test that asserts format `^1\d{2}\d{2}\d{3}$` and uniqueness.
ex: ts | Construction and validation
const code = makeErrorCode(3, 4, 2);                 // "10304002" -> platform 1, service 03, module 04, seq 002
export const makeErrorCode = (ss: number, mm: number, seq: number) =>
  "1" + String(ss).padStart(2, "0") + String(mm).padStart(2, "0") + String(seq).padStart(3, "0");
it("codes are unique and well-formed", () => {
  const nums = Object.values(EC).map((e) => e.num);
  expect(new Set(nums).size).toBe(nums.length);
  nums.forEach((n) => expect(n).toMatch(/^1\d{2}\d{2}\d{3}$/));
});
/ex
fail:
- A duplicate code is a build failure (test), not a runtime concern.
test:
- Format, uniqueness, banding (if used), status/category consistency.
anti:
- Hand-concatenating with `||` fallbacks.
- Different `SERVICE_CODE` in logger vs catalog.
- Reusing a retired number.
- Inventing a new code format.
check:
- 8 digits; unique; constant `SERVICE_CODE`; test; no legacy scheme used.

ex: ts | Error middleware (reference, condensed)
export function errorMiddleware(err: unknown, req: Request, res: Response, _next: NextFunction) {
  const correlationId = req.correlationId ?? getCorrelationId() ?? "unknown";
  const appError = err instanceof CorsRejectedError ? corsAppError() : toAppError(err);
  const meta = { correlationId, method: req.method, route: req.route?.path ?? req.originalUrl.split("?")[0],
                 statusCode: appError.statusCode, code: appError.code, details: appError.details, err: serializeError(err instanceof Error ? err : new Error(String(err))) };
  appError.statusCode >= 500 ? logger.error(meta, "Unhandled error: " + appError.message) : logger.warn(meta, "AppError: " + appError.message);
  return res.status(appError.statusCode).json({ success: false, ...formatError(appError, correlationId) });
}
/ex
